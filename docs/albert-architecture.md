# Albert Architecture and Design

**Last updated:** 2026-06-19

Albert is a local coding-agent orchestrator MVP. It turns local markdown PRDs and Issue Slices into a mission-control workflow where a user approves bounded work, Qwen routes approved slices to the right local model tier, Local Agents work in isolated worktrees, Evidence Packages gate review, and PR-ready summaries are prepared without automatic merges.

## Core Design

Albert keeps the Orchestrator as the authority. Models can plan, route, implement, or review within their role, but the Python runtime owns contracts, lifecycle state, launch blocking, command policy, evidence validation, repair routing, and PR preparation.

The current MVP is intentionally dependency-free Python stdlib:

- Local tracker records live under `.scratch/`.
- App runtime JSON and bulky evidence live under the configured `--runtime-root`.
- Mission records generated by Albert can be written into the target repo.
- Agent worktrees are created outside the target repo under `.albert-worktrees`.
- The TUI is textual and command-driven until the command semantics settle.

## Mission Control App

The approved product direction adds a Tauri desktop shell and React/TypeScript interface over the existing Orchestrator. The Orchestrator remains the authority through a long-running local backend that provides an initial state snapshot and batched event stream; the frontend presents state and submits semantic actions rather than owning accepted mission state. See ADRs 0001-0003 for the desktop stack, persistence model, and provider boundary.

The interaction direction is Variant A, Command Deck, under `@visualization/albert-mission-control/`. The prototype validates interaction responsibilities only and is not production architecture.

The app has two persistent operational lanes:

- The left lane defaults to the Agent Console and can switch to the distinct Shell Terminal mode.
- The right lane is a focused Operations Workspace where each view presents one primary object rather than acting as a comprehensive dashboard.

Operations Workspace responsibilities are separated deliberately:

- A compact mission selector changes the Active Mission without resetting the Workspace Session.
- Mission Board presents the Issue Graph, concise progress, and Issue Slice lifecycle state.
- Selecting an Issue Slice opens an inspector for attached sessions, role/model provenance, accepted boundaries, evidence summary, and Working Context sources.
- Review Workspace contains evidence acceptance, repair, and human-escalation decisions.
- Workspace Queue exclusively contains Issue Change Proposals, Frontier Confirmations, and Ad Hoc Delegation approvals; other views expose only compact attention links.
- Activity presents the searchable Activity Journal chronologically.

Conversation Scope is independent from navigation. Its user-facing targets are Working directory, Mission, and Issue Slice, and changing the visible mission or selected item does not silently retarget an unfinished message. Scope influences Working Context and message interpretation but never grants launch authority, expands permissions, or mutates locked mission state.

Issue lifecycle labels preserve governance semantics: Ready means approved, unblocked, and eligible to launch; Complete means work is finished, its Evidence Package is accepted, and it is PR-ready, not merged.

The visual direction is an industrial command deck: high contrast, restrained lime and cyan accents, dense precise information, and purposeful motion. Borders and uppercase metadata remain subordinate to primary content hierarchy.

## Runtime Flow

1. Load a PRD and Issue Slices from a tracker directory.
2. Parse blockers into an ordered Issue Graph.
3. Let the user inspect, assign, approve, reopen, route, launch, review, repair, and prepare PR-ready work through CLI/TUI commands.
4. Lock approved Issue Slice contracts so goal, blockers, acceptance criteria, risk, classification, and evidence requirements do not drift accidentally.
5. Route approved work through Qwen when escalation decisions are needed.
6. Launch bounded Local Agent sessions in isolated worktrees.
7. Collect or validate Evidence Packages with changed files, diff summary, commands, test results, risks, context updates, and artifacts.
8. Record Frontier review outcomes: approved, approved with limitations, needs repair, needs human review, or rejected.
9. Relaunch repair sessions with prior review, evidence, and artifact context when review is repairable.
10. Prepare branch and PR instructions while keeping final merge authority with the user.

## Code Boundaries

- `albert_mvp/core.py` contains the domain model: PRD loading, Issue Slice parsing, lifecycle state, approval locking, Qwen-controlled delegation, session launch, runner execution, evidence validation, review outcomes, repair relaunch, mission records, and PR prep.
- `albert_mvp/agents.py` loads and validates the agent registry.
- `albert_mvp/tui.py` builds textual mission-control state and implements TUI-backed actions.
- `albert_mvp/cli.py` exposes the command surface.
- `tests/test_albert_mvp.py` provides acceptance coverage for the MVP workflow.
- `.albert/agents.json` is the current local model registry.
- `.scratch/local-coding-agent-mvp/` contains the product workflow PRD and completed MVP Issue Slices.
- `.scratch/local-coding-agent-mvp-development/` contains the completed implementation roadmap.

## Model Roles

The current registry uses local Ollama models:

| Agent id | Ollama model | Albert role | Routing role | Visibility |
| --- | --- | --- | --- | --- |
| `qwen3.6-27b` | `qwen3.6:27b` | `frontier` | `router` | Routing/frontier decisions |
| `gemma4-12b` | `gemma4:12b` | `local-agent` | `worker` | Normal assignment |
| `gemma4-26b` | `gemma4:26b` | `local-agent` | `worker` | Normal assignment |
| `qwen2.5-coder-14b` | `qwen2.5-coder:14b` | `delegate-agent` | `delegate` | Delegate-only |
| `deepseek-r1-14b` | `deepseek-r1:14b` | `delegate-agent` | `delegate` | Delegate-only |

Delegate-only agents are hidden from normal manual assignment. Qwen must choose them through `route ISSUE_ID` before launch. The approval gate still exists for configured gated or cloud delegates, but the default delegates are local models.

## Design Constraints

- Frontier approval means PR-ready, not merge-approved.
- One Issue Slice maps to one primary Local Agent by default.
- One Issue Slice maps to one PR by default unless a human approves grouping.
- Runtime state and large artifacts stay outside the target repo.
- Mission Markdown should stay navigable and link to evidence instead of embedding raw logs.
- Command execution is classified as `auto-allowed`, `frontier-approvable`, or `human-required`.
- File visibility is modeled as `Normal`, `Local-only`, or `Blocked`.
- Accepted worktrees are cleanup-eligible, but MVP cleanup is user-triggered.
